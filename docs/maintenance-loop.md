# Project maintenance loop

This mechanism centers on “read project memory for every change, update project memory for every retrospective.” `AGENTS.md` handles routing; `docs/subsystems/` records current system facts; `docs/code-standards.md` stores general and promoted stable rules; `LESSONS.md` stores recent evidence-backed lessons. They link to one another without redefining the same content.

## 1. One-time initialization (Bootstrap)

The agent first inspects the repository entry points, existing rules, package/build manifests, CI workflows, test configuration, code directories, and necessary key implementations. Based on this, it fills in `docs/project-profile.md`, lists verified validation commands and permission boundaries, identifies subsystems by runtime responsibility rather than directory name, and writes current-behavior references for each subsystem with an independent contract. It records conventions, CI checks, and security risks that actually exist in the project in the code-standards and contributors documents. Every conclusion must link to source, test, or configuration files.

Do not fill template `UNKNOWN` values with guesses, create release gates that do not exist, or copy subsystem details from other projects. Mark unverifiable content as unknown; leave product tradeoffs and autonomous permissions for maintainer confirmation. Until initialization is complete, the project must not call the template rules customized project standards.

## 2. Each development task

At the start, follow `AGENTS.md` to read the profile, Lessons, applicable standards, and subsystem pages. Trace behavior completely from external entry points through state writes, outputs, and side effects; check analogous entry points and boundary conditions; reproduce first and then modify according to actual risk. When fixing a defect, reproduce it using the reporter's actual surface and original inputs where possible; record specific limitations when conditions are insufficient or reproduction is impossible, and do not present speculation as resolved. Include tests with code changes; when fixing behavior, verify where possible that the regression test fails under the old behavior. When interfaces, state, compatibility, permissions, or failure modes change, update the relevant subsystem page in the same change.

When complete, run the checks specified by the profile against the current review HEAD. Commits/PRs must state the commands and results actually run, items not run and why, and the reviewed SHA. If HEAD changes during checking, review and validate the new HEAD again. When no real integration or platform environment is available, say so plainly; do not substitute unit tests for real-use validation.

## 3. PR / external contribution review

Read `docs/contributors.md` first for security and scope triage, then review the target against code-standards and subsystem refs. Do not review only the diff: verify the claimed behavior and call chain, affected sibling cases outside the change scope, platform/client variants, fallbacks or alternative implementations, and consistency of documentation and tests. If code, tests, CI, or documentation show conflicting rules, report the conflict and correct the single authoritative location. When project-profile escalation conditions apply, a product issue requires an owner decision, or an operation exceeds the permission boundary, stop at the recommendation stage.

## 4. Daily commit retrospective

Each day, an agent authorized to read repository history and validation results must first run `python3 scripts/freeze-review-range.py --repo .` and use its canonical manifest as the sole range authority. Do not calculate the range from `LESSONS.md` or a later `HEAD`. If `reviewed-through` is `UNKNOWN`, stop and ask a maintainer for the first target-branch commit to include; its target-branch parent is the exclusive boundary (for a merge, use the target-branch parent, normally first parent). Never guess or initialize the watermark automatically. The commit list contains every commit in the frozen range; `excluded_paths` records individual paths excluded by the committed policy, not commits removed from the range. Before opening a patch or file, match commit/parent/path records and skip the contents of excluded paths for those comparisons. Review non-excluded changes in the same commits, and record excluded paths and policy reasons in the archive.

Prioritize errors in development, code review (CR), merge/release, and verification: repeated rework, changes that should not have been merged/released, and insufficient validation; also record `Done right`. Do not review the contents of generated data excluded by the frozen manifest as Lessons, whether pulled/generated/committed by a daily action or produced by training, an intermediate stage, ETL, a script, runtime behavior, or another process. A generated-data or workflow anomaly may be recorded as an automation-health/verification issue only with independent workflow, CI, validator, or similar evidence. Every Lesson must be grounded in project evidence and include an executable rule. State a cause only when the evidence supports it. Otherwise, record the observed event and the specific open questions that must be answered to determine the cause; do not infer causation from timing or correlation alone. Even when a review finds nothing, archive its scope, exclusions, sources checked, and the no-new-lesson result.

Record distinct dates according to `LESSONS.md`. By default, promote the same lesson to a stable project-specific code-standards rule only after it appears on at least three independent review dates. A serious one-time risk may be proposed as a temporary rule, but mark it as pending owner confirmation. After promotion, retain source dates and evidence; do not delete the historical trail. Do not directly edit the archive, `LESSONS.md`, or `docs/code-standards.md` during the review: provide UTF-8 archive and active Lessons content files to `python3 scripts/write-frozen-review.py` with the exact frozen manifest and configured archive path. For an eligible promotion, also supply both complete promoted-Lesson and promoted-standard content inputs; the writer moves the promoted Lesson ID out of active history and upserts both promotion blocks by range key. The writer verifies the archive and all requested memory updates and advances `reviewed-through` to the manifest's `through` only as its final durable write. If freezing, writing, or verification fails, stop and preserve the previous watermark; never update it manually.

## 5. Periodic calibration

Maintainers or agents periodically check whether Lessons have been promoted or invalidated, standards are covered by implementation/CI, subsystem facts have drifted from the code, links and commands remain valid, and `reviewed-through` does not omit commits. Explicitly revise or archive outdated rules; do not let documentation grow without limit merely to appear complete.

## 6. Automation integration

The template provides reusable prompts, [`automation/runner-contract.md`](automation/runner-contract.md), `scripts/freeze-review-range.py`, and `scripts/write-frozen-review.py`, but does not bind any particular model, scheduled service, or token, nor imply that a scheduled agent is configured. The installable `.github/workflows/lesson-promotion-gate.yml` checks persisted Lesson-promotion records only; it is not a daily-review runner. After selecting the actual scheduler, the project owner sets the time zone, read-only/write scope, run branch, report destination, and matters requiring maintainer involvement. Resolve an `UNKNOWN` watermark only through an explicit maintainer decision before the first range-dependent run. After that boundary is established, first verify scope, exclusions, boundary handling, and privacy in read-only mode; the freezer itself never writes or advances the watermark. Only then open permissions for writing documentation, opening PRs, and similar actions.
