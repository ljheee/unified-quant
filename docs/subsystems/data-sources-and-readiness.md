# Data Sources, Calendars, and Training Readiness

> Current behavior reference. Last checked: `2026-11-02` against the uncommitted worktree based on HEAD `22d2121c2eeab5c6b4b792dcfce7dc388b50b56b`. Based on source code, documented measurements, and tests; unverified items are marked `UNKNOWN`.

## Responsibilities and Boundaries

This page covers the parts that decide what the platform *may* believe: vendor source adapters, the trading-session calendar and its provenance, lifecycle classification of missing rows, and the pre-training readiness gate over governed inputs. It is the evidence layer for `docs/subsystems/ingest-and-canonical-store.md` and for `docs/subsystems/model-layer.md`.

It does **not** own routing decisions (the router consumes the calendar, the calendar does not decide routing) and does not own factor or model computation.

## Primary Runtime Paths

**Adapters** implement `fetch(dataset, instruments, start, end, fields) -> FetchResult`, returning rows plus a typed status, delivered-field set, optional raw payload bytes, and warnings/errors. The router rejects an adapter whose `source_name` disagrees with its registration key, so envelope identity is enforced at the boundary.

**Calendar.** `TradingCalendar` is a thin predicate over an explicit session provider. `EastMoneySessionProvider` derives sessions from a third vendor's index klines so a wrong session list cannot cancel itself out between two bar vendors, and it only certifies the contiguous range its payload actually covers: a window reaching past the newest published bar raises `IndependentCalendarError` rather than returning an empty, coverage-passing set.

**Lifecycle.** When a verified-only row gap appears, `AkShareLifecycleProvider.classify_missing` and `.suspension_window` classify it (suspended, not listed, delisted, unknown). A gap that cannot be explained fails closed unless `allow_unknown_missing` is configured; an explained gap is reported as a warning, not silently dropped.

**Readiness.** `assess_readiness` is pure and fail-closed: PIT membership per session, required bar fields present and non-null, bar gaps reconciled against governed suspension evidence, label horizon reaching far enough that the last sessions are trainable, and factor/label linkage. A canonical row explicitly marked `suspended` agrees with a suspension record; a row with another status (including `unknown`) on that session is a conflict. Without suspension data, active-period gaps remain blocking as `unverified_bar_gap`. Since Tushare `suspend_d` may omit intermediate sessions of a multi-week halt, `--suspension-interval-evidence` can add date intervals supported by issuer or exchange notices; the report binds the input file SHA-256 and citations, and the intervals expand only over declared calendar sessions. It supplements, never replaces, live or snapshot suspension evidence, and cannot be combined with `--skip-suspensions`. A verified immutable `stock_basic(list_status=D)` snapshot can date-bound absence: missing required sessions on or after the effective `delist_date` are informational, while gaps strictly before that date remain blocking. The readiness CLI records the walk-forward warmup length; an instrument whose entire PIT membership ends before the first model-visible session may have short history in the warmup only, which is reported informationally. Short-history instruments with membership at or after that boundary remain blocking. Excluded instruments are an explicit, auditable parameter; an excluded instrument that actually has no gap is itself a blocking finding, so the exclusion list cannot quietly shrink the universe.

## Multiple Implementations / Entry Points

- **TDX daily bars use the MAC client; XDXR remains on the standard protocol.** `MootdxSourceAdapter._client()` uses easy_tdx `MacClient` 1.1.0 pinned at commit `4820b4a0496899ece0b8ca4d7f4d66a5159da7f8`; it tries `DEFAULT_MAC_SERVERS` in order and accepts a host only after a full-page `600000` daily-bar response with the required columns. On 2026-11-02 all three configured MAC hosts returned 800 rows for that probe. `fetch()` maps MAC `vol` directly to canonical `volume` because the MAC value is shares; it does not apply the standard-protocol lots-to-shares multiplier. The separate `_xdxr_client()` continues to use mootdx and the standard-protocol server list. On 2026-11-01, 38 mootdx HQ hosts answered the security-count probe but full-page `600000` bars returned empty on all 38; standard-protocol XDXR still returned 88 rows on two measured hosts. These are time-bounded, command-specific observations, not a permanent availability claim.
- **Tushare tiers differ.** `TushareFreeAdapter` shares the implementation in `TushareAdapter`; `Tushare2kAdapter` is the 2000-point account used for index membership, `adj_factor`, `stk_limit`, `suspend_d`, and bounded research inputs. The adapter reads `TUSHARE_2K_TOKEN` from process environment only. The CLI does not load `.env`; an operator must inject the value at process startup. Live-fetch launchers may parse only that key from `.env` and pass it through the child process environment without printing or persisting the value.
- **Supplemental research data is a raw-source layer.** `research_data()` allowlists `stock_basic`, `suspend_d`, `daily_basic`, SW industry classification/membership, standard statements and indicators, company forecast/express, seller forecasts (`report_rc`), `moneyflow`, `hk_hold`, and `top_list`; a bounded query filter is mandatory. `TushareDependencyStore` preserves the exact query and response bytes as immutable, checksum-verified Parquet snapshots. `stock_basic(list_status=D, fields=ts_code,list_status,list_date,delist_date)` supports reproducible lifecycle classification; daily `suspend_d(trade_date, suspend_type=S)` responses can be snapshotted per session for offline readiness replay. Neither endpoint certifies historical universe membership or PIT features. These raw responses are not normalized canonical factors and do not certify PIT availability. The fetch scripts read `TUSHARE_2K_TOKEN` from the process environment and do not load `.env` themselves.
- **Truncation checks are deliberately partial.** `_RESPONSE_LIMITS` currently covers 7 of the 15 dependency endpoints, including the 6,000-row `stock_basic` and 5,000-row `suspend_d` limits. The remaining financial-statement and forecast endpoints have no local response-cap detector; bounded query filters do not prove that a provider response was not truncated. Do not treat these snapshots as complete solely because publication succeeded.
- **Endpoint timing remains a consumer responsibility.** Daily indicators, money flow, and top-list data are available after close; `hk_hold` is published the next morning. Do not use them for same-session open decisions. `index_member_all` contains `in_date`/`out_date` but no historical provider-publication vintage, so its valid-time history alone does not establish transaction-time PIT. `report_rc` at 2000 points is a 10-request/day trial, insufficient for a full historical analyst-expectation panel; analyst expectations are optional model features, not a prerequisite for the Alpha158 linear-vs-LightGBM comparison.
- **AkShare is an optional dependency and is not installed** in `.venv` or `.venv-qlib` (verified by import). It is only reached through the lifecycle provider and the optional `akshare_calendar` helper; the default v2 path uses EastMoney instead. Any claim that AkShare ran must name the environment it ran in.
- **Two calendar shapes:** an injected `set[date]`, or a provider callable. A sessions-only calendar has no evidence payload, so `provenance` is recorded as `unspecified` — which is itself audit-relevant.
- **Independent-calendar opt-out is recorded honestly.** With `--skip-independent-calendar`, the manifest carries `independent_source: not_checked` and `cross_check_result: skipped`, never a fabricated `agreement`.

## State and Data Contracts

Calendars are stateless except for the EastMoney provider's cached, self-certifying contiguous range (earliest session plus payload digest), which is pinned into the ingest report as `calendar_evidence` so coverage completeness is auditable after the fact.

Supplemental Tushare snapshots live under the user-selected source-data root, separate from canonical bars. Generation identity binds endpoint, query, and Parquet checksum; identical responses are idempotent and changed provider responses create a new generation. Each staged Parquet file and manifest is read back and checked before the generation directory becomes visible. The store indexes a new publication in the same process so a later exact-query lookup can resume without refetching. It verifies the newest recorded response and fails closed if that response is corrupt; it does not silently fall back to an older provider revision. `validate_training_readiness.py --delisting-snapshot-generation <id>` reads a checksum-verified D-status snapshot and records its generation and fetch time in the report. `--suspension-snapshot-root <source-root>` requires and reads one exact `suspend_d(S)` snapshot for each governed session, records the full input set digest, and never falls back to live responses for a missing session. `--suspension-interval-evidence <json>` adds source-cited issuer/exchange date ranges, validates their schema and source domains, expands them over the current calendar, and records the source file digest and citations in the report. This is needed when the Tushare daily suspension feed omits sessions inside an ongoing halt; it does not edit raw snapshots or canonical bars. Missing sessions on or after an effective delisting date are informational; missing sessions strictly before it remain blocking. `--warmup-sessions` records the walk-forward warmup; short history is informational only when an instrument's PIT membership ends before the first model-visible session. `build_tushare_factor_candidates.py` can derive lagged valuation, turnover and money-flow candidate features plus market-cap/liquidity exposure Parquet from exact-date snapshots. Its immutable bundle binds every source snapshot and canonical calendar partition, but always sets `historical_vintage_verified=false` and `strict_pit_eligible=false`: the local historical responses were fetched after their represented sessions, and an assumed next-session visibility does not prove historical provider vintages. Downstream factor/exposure publishers still require their owning schemas, source approval, PIT timing, and external quality review. Candidate factor and exposure files are also read back before atomic publication.

Market dataset families published for paper execution (`trading_calendar_snapshot_v1`, suspension and corporate-action sets) are immutable manifest-first snapshots from `MarketDatasetPublisher`, read through `PublishedPaperMarketData` as ordered partition-set triples with a digest convention shared with the set-binding resolver.

## Constraints, Failures, and Compatibility

- **No degradation to a smaller expected set.** Any transport, parse or coverage failure in the independent calendar raises; shrinking the expected set would make `observed >= expected` trivially true and publish unverified data as complete.
- **`adj_factor` flat at 1.0 is not a defect signal.** Measured: in one full-A session, 62 of 5059 instruments never had a corporate action. Validation must distinguish "correctly flat" from "should have adjusted but did not" (`docs/user-guide.md` §5.2).
- **A source's coverage gap must be declared, not inferred.** A missing `suspend_d` row does not prove that a stock traded: Tushare can omit intermediate dates of a long halt. Unexplained bar gaps remain blocking unless daily suspension rows or source-cited interval evidence explain them; do not exclude a name when a verified halt interval covers the dates (`docs/user-guide.md` §5.4).
- **Suspension and bars from the same vendor can mask each other.** The readiness gate unions daily `suspend_d` rows with verified interval evidence and rejects contradictory canonical rows, including rows whose status is not `suspended`. Daily rows alone remain a same-vendor check; a correlated vendor fault could still hide an ingest gap.
